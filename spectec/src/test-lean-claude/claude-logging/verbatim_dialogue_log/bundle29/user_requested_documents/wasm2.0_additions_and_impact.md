## 6. Downstream impact (estimate)

Method: `B/tools/cascade29.py` compiled each downstream module, in import order, in the scratchpad against
the final model. Every declaration with an error first gets `sorry` as its proof; if its statement still
fails, it is deleted; repeat until the module compiles, then go on to the next module. "Broken" = sorried +
deleted. The bundle23 column is the same cascade against the bundle23 regenerated model.

Total: 104 of 856 downstream declarations break (12%), almost all in
`TypeProgress` (91 of 298) and `TypePreservation` (12 of 135). `HelperLemmas`, `Subtyping`, `TypingLemmas` and
`TypePreservationPure` compile unchanged.

Root causes (first error of each broken declaration):
- Functions that are now relations, used downstream as functions (most of it; already the case for the
  bundle23 model): field access on `fun_table`/`fun_mem`/`fun_global` results (`.REFS`, `.BYTES`, `.VALUE`),
  `sizenn`/`lsize`/`lsizenn`/`jsize` (now `fun_sizenn`, …), `with_global`/`with_table`/`with_mem`/`with_elem`/
  `with_data`, `vvunop_`/`vvbinop_`/`vvternop_`, `unop_`/`testop_` (now `Option … → Prop` relations).
- New with this regeneration: `fzero` → `fun_fzero` (`num_default`, …) and `default_` → `fun_default_`
  (`default_val_ok`, `default_vals_ok`, `default_not_none`, `t_progress_e_call_addr`).
- Changed constructor premises (`Application type mismatch`, `Insufficient number of fields`): mostly in
  progress proofs that build `Step_read`/`Step_pure` derivations, which now need the relational premises
  (e.g. a `fun_table` witness, `fun_default_` for every local, the restored length premises).
- Knock-on effects: declarations whose statements were deleted (e.g. `bt_inversion` in `ExtensionLemmas`,
  `default_val_ok`) break their users.

By role (counted from the cascade report):
- `TypePreservation` (12): 3 preservation cases (`t_preservation…`/`t_read…`) and 9 auxiliary lemmas
  (`default_val_ok`, `default_vals_ok`, `num_default`, `num_default_is_well_formed`, `table_grow_store_ok`,
  `memory_grow_store_ok`, `with_mem_store_ok`, `reduce_inst_unchanged_aux`, `store_extension_reduce_aux`).
  Mostly mechanical: obtain the relation's witness instead of applying the function.
- `TypeProgress` (91): 44 progress cases (`t_progress_be_*`, `t_progress_e_call_addr`) and 47 auxiliary lemmas
  (lane/size facts such as `wf_lane_Jnn_inv`, `jlane`, `flane`; totality facts such as `binop_total`,

## 7. Observations (non-blocking)

- Float lanes: the float constructors of `fun_vunop_`/`fun_vbinop_` (e.g. `fun_vunop__case_12`) compute
  `Option.get! (proj_lane__1 l)` with no `proj_lane__1 l ≠ none` premise, while the integer constructors have
  `proj_lane__0 l ≠ none`. This is pre-existing: `OLD_wasm2.0.lean`, the bundle23 model and this one all
  have 168 such `get!`s and the same guard counts. It only matters for ill-formed inputs (a non-float lane in
  a float shape); no theorem depends on it, and the audit shows no proof uses a default value. It is a
  remaining spot where the model's indexing is not fully principled.
- `DefToRel` still emits iterated calls twice (`var_2_lst` for the wf premise, `var_0_lst` for the result);
  the proofs use the length premise of the latter.
- `wasm2.0_prevattempt.lean` is the bare bundle23 regenerated model (90 `sorry`s, md5 `72748a07…`), not the
  half-finished attempt (that one only ever existed in the scratchpad).
